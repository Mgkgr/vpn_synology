# Изолированный стенд ByeDPI

Это **не рабочий третий маршрут**. `compose.staging.json` намеренно использует
`network_mode: none`: можно проверить локальный TCP-тракт, но нельзя открыть
сайты. В основной Compose и Mihomo службы не добавлены. Не заменять этим стендом
действующие WireGuard/Mihomo и не включать для него автоперезапуск.

Выбран предусмотренный планом резервный движок ByeDPI: штатная конфигурация
ядра DS923+ не содержит необходимых для согласованной схемы Zapret2
`owner`/`CONNMARK`. Это не означает, что NFQUEUE вообще не работает.
Подробности и доказательства: [отчёт](../../docs/diagnostics/2026-09-28-antidpi-staging.md).

## Состав

- `antidpi`: ByeDPI 0.17.3, принимает только `127.0.0.1:1081`, без UDP и доменных
  SOCKS-запросов по умолчанию. Domain-режим проверен отдельным DNS harness,
  но в этот Compose не включён. Фиксированная тестовая стратегия `--split 1` ещё не проверялась
  на обходе DPI и не является автоматически выбранной стратегией.
- `socks`: отдельный Mihomo 1.19.28 в том же новом namespace; только парольный
  SOCKS на 1080 → ByeDPI. Нет `DIRECT`, controller, TUN и слушающего DNS.
  При потере обработчика supervisor закрывает процесс прокси и его соединения.
- `healthcheck.py`: проверка SOCKS-протокола и авторизации, а не доказательство
  доступа к Интернету. Прикладные проверки сайтов будут отдельным уровнем.

Оба процесса работают как `10002:10002`, без capabilities, с read-only rootfs,
ограничениями памяти/PID/tmpfs/логов, без host network, опубликованных портов,
Docker socket или `privileged`. CPU CFS limits не используются: NAS их не
поддерживает. SOCKS-секрет генерируется отдельно, имеет режим `0600` и владельца
UID 10002; не хранится в Compose, Git, environment или командной строке.

## Артефакты и воспроизведение

`versions.json` содержит проверенные версии, commit и SHA-256 исходного/релизного
архивов и бинарника. Базовые образы закреплены registry digest. Конечные образы
пока локальные: закреплены реальными Docker image ID с `pull_policy: never`,
публикации в registry и выдуманного RepoDigest нет.

В `.artifacts/` помещаются проверенный `ciadpi-x86_64`, его MIT `LICENSE` и
официальный `MIHOMO-LICENSE`; бинарники и секреты исключены из Git. Корень контекста
— этот каталог. `build-antidpi-staging.py` принимает только заранее проверенный
архив контекста с фиксированным хешем, копирует allowlist обычных файлов в
закрытый root-owned каталог, сверяет уже установленные базовые образы и выполняет
сборку без сети/pull. При изменении исходников хеш контекста требуется повторно
проверить и явно обновить, а не отключать контроль.

`probe-antidpi-staging.py --approved <reviewed-build-id>` — ручная приёмка из
существующей root-консоли NAS. Создаёт только три временных помеченных контейнера
(обработчик, auth-прокси, локальный echo-клиент), проверяет авторизацию, 256 КиБ
двусторонней передачи и отказ при остановке **тестового** обработчика. Удаляет
только собственные ID после проверки меток. Сверяет пять рабочих контейнеров,
правила firewall и маршруты до/после. Не является общим root API для панели.

`probe-antidpi-dns-lifecycle.py --approved <reviewed-build-id>` проверяет настоящий
Mihomo FakeIP/classical rule-set на искусственных доменах, передачу по доменному
SOCKS-запросу, FakeIP/NXDOMAIN/отказ DNS, затем смену namespace при recreate и
stop/start обработчика. Planner требует пересоздать auth-прокси с новым owner ID
и сверить живые namespace; один `depends_on` этого не обеспечивает.
Есть отдельный lock приёмки и тесты cooldown, но production boot/watch ещё нет.
[Фактические результаты и оставшиеся ограничения](../../docs/diagnostics/2026-09-28-antidpi-dns-lifecycle.md).

## До подключения третьего маршрута

1. Применить проверенный на стенде DNS-контракт к реальной схеме только после
   контроля DNS drift, двойного разрешения и исключения DNS control-plane из
   antiDPI. Основной DNS не менялся. Production DNS/UDP readiness — `false`;
   `offline_dns_contract_verified=true` не разрешает направлять клиентов.
2. Проверить реальный TCP/TLS/DPI-трафик на согласованных сайтах; если UDP не
   поддержан выбранной схемой, явно оставлять его на VPN, без молчаливого DIRECT.
3. Подключить проверенный scoped recovery к общей блокировке обслуживания и
   boot/watch задаче. Namespace recovery и закрытие старого входа проверены
   вручную на стенде, не при reboot NAS и не установленной автоматикой.
4. Подключить reviewed maintenance contract, backup/restore и health-state;
   только после этого регистрировать маршрут и UI. Текущие fallback и правила
   на стенд не направлены.
