# Anti-DPI runtime: незавершённая приёмка 08.10.2026

Работа выполнялась в текущем checkout без агентов. Это отчёт о частично
выполненном развёртывании, не подтверждение готовности автоматической смены.

## Что сделано на NAS

- Проверен доступ через LAN и уже открытую пользователем root SSH-сессию.
- Перед установкой создана локальная зашифрованная restic-копия и выполнена
  файловая проверка восстановления. Рабочие базы не восстанавливались.
- Первый backup был отклонён из-за несовпадения схемы dashboard. Сравнение с
  последней проверенной копией обнаружило только 11 известных новых таблиц и
  4 индекса мониторинга/обслуживания; удалений и изменений прежних объектов нет.
  Обновлена только проверенная запись схемы; прежний manifest сохранён приватно.
- Созданы отдельные контейнеры `vpn-antidpi` и `vpn-antidpi-socks` с закреплёнными
  локальными image ID, без опубликованных портов и Docker socket, от UID 10002,
  read-only rootfs, без capabilities. Четыре стратегии имеют отдельные процессы.
- Установлена `vpn-maintenance.service`. Сбой `enable --now` на systemd 219
  устранён отдельными `enable` и `start`; подтверждены `enabled` и `active`.
- Автополитики остаются выключенными, `apply_ready` не выставлен. Никакие сайты
  или WireGuard-клиенты на новый выход не переключались.

## Что выявлено при живой проверке

1. Один и тот же Docker inspect возвращал два порядка `Mounts`; при неизменных
   образе, правах и путях это давало два разных хэша конфигурации. Локально
   исправлено каноническим порядком списка с сохранением проверки всех полей.
2. Контроллер DNS возвращал, в том числе, TTL=1 для Discord, Telegram и Instagram.
   В этой версии Mihomo истёкший кеш может возвращаться с TTL=1, пока обновляется
   upstream. Это поведение подтверждено [исходником resolver](https://github.com/MetaCubeX/mihomo/blob/v1.19.28/dns/resolver.go#L141).
   Локально добавлены параллельные запросы пяти фиксированных имён и максимум
   три попытки для слишком короткого TTL; искусственное продление запрещено.
3. Расписание писало состояние выключенных политик каждую секунду. Локальная
   регрессия теперь исключает эти лишние записи. Во время диагностики был
   замечен `database is locked`; уменьшение записей ещё нужно проверить на NAS,
   причинная связь с этим сообщением пока не доказана.
4. До установки тестом обнаружен отсутствующий `antidpi` image ID в manifest
   резервной копии стратегии. Исправлено; тест реально проверяет копирование
   SQLite, manifest и восстановление, подменён только носитель архива.

## Подтверждённое ограниченное обновление

Первый запрос обновления установленного root-worker был остановлен проверкой
безопасности. После отдельного подтверждения владельца «делай» 08.10 выполнено
именно ограниченное обновление новой службы, без обхода прежнего отказа:

- Предварительно проверены точная identity прежней установки, SHA256 архива,
  отсутствие добавленных/удалённых файлов и ровно четыре изменённых модуля.
- Хеши Docker мигрированы только после доказательства, что прежний хеш совпадает
  с одной из двух перестановок тех же mounts. Изменение образа, пути или RW
  не принимается за перестановку; четыре отдельных теста проверяют эту границу.
- Остановлена только `vpn-maintenance.service`. До записи создана зашифрованная
  копия исходников, настроек runtime, приватного состояния и согласованный
  SQLite snapshot; выполнена проверка расшифровки и восстановленных файлов.
- Обновлены `docker_control.py`, `host_install.py`, `host_service.py` и
  `strategy_schedule.py`; служба вновь запущена и имеет статус active/enabled.
- Время запуска и RestartCount `vpn-wireguard` и `vpn-mihomo` до и после совпали.
  Панель также остаётся running. Автополитики выключены, подтверждения приёмки
  не подменялись. Старые bootstrap-ошибки сохранены как история попыток.

Архив исходников обновления:
`8ad3efc954530d99cd4a2c640e90117ba09a811cbd1ee56c01c512a65a7e3387`.
Приватная квитанция с точным snapshot ID находится на NAS в
`/volume1/docker/vpn-dashboard-maintenance/private/updates/antidpi-<SHA256>.json`.

## Проверка после обновления

Трёхминутное наблюдение с шагом 10 секунд: 19 замеров, шесть разных DNS-снимков;
семь замеров пришлись на просроченный снимок. `can_check` переходил в false,
`can_apply` всё время false, включённых политик ноль. И начальная, и конечная
проверки Docker подтвердили правильные контракты и общий namespace новой пары.
Это не тест восстановления namespace после аварии.

В период действующего DNS-снимка отдельные запросы через **реальный вход новой
пары на NAS**, с проверкой TLS и без redirect, получили HTTP 200:

| Контрольный сайт | Задержка одной пробы |
| --- | ---: |
| www.youtube.com | 222 мс |
| discord.com | 205 мс |
| web.telegram.org | 303 мс |
| www.instagram.com | 888 мс |

Это по одному HTTPS-запросу с NAS, не приёмка приложений или WireGuard-клиента.
От `10.66.0.4` проверено только установление TCP к приватному адресу входа;
аутентифицированная сквозная проба ещё не выполнена.

Повторные запросы существующего DNS API показывали убывающий TTL: например,
YouTube 21→19→17 секунд, IPv4 Instagram 20→18→16. Три ограниченных повтора не
обеспечили непрерывность снимка. API вызывает кеширующий `ExchangeContext`,
а досрочное обновление кеша этим запросом не предусмотрено: [DNS API](https://github.com/MetaCubeX/mihomo/blob/v1.19.28/hub/route/dns.go),
[resolver](https://github.com/MetaCubeX/mihomo/blob/v1.19.28/dns/resolver.go#L141).
Это ограничение **нового Anti-DPI DNS-механизма**, не доказательство сбоя
действующих VLESS/HY2. Истечение любого из пяти имён сейчас закрывает общий вход.

После этой серии владелец отдельно согласовал предварительное DNS-обновление
контрольных имён Anti-DPI с прежними запретами private/FakeIP/stale. Основной DNS
клиентов и VPN-маршруты не меняются. Результат следующего этапа приведён ниже.

## Независимый DNS — согласованное продолжение 08.10

Установлен отдельный host-side refresher пяти фиксированных имён. Используются
Cloudflare и Google DoH по TLS с фиксированными bootstrap IP, без DNS/proxy
окружения и redirect. Проверяются вопрос, связная A/CNAME-цепочка, публичные
IPv4, TTL и HTTP Age. Каждый адрес имеет собственный абсолютный срок; при
отказе источников можно использовать только ещё не истёкший ответ. Перевод
часов назад аннулирует память предыдущего поколения. Истечение не маскируется
продлением TTL; потребители по-прежнему закрываются при недействительном DNS.

Второй источник используется при отказе, коротком TTL или смене адреса.
Предварительное обновление выполняется в отдельном потоке и не ждёт Docker
health-check. Формат runtime-снимка не изменён, новые порты не открывались.

На NAS все десять запросов preflight (пять имён × два источника) прошли за
168–263 мс каждый. После свежей зашифрованной копии с проверкой восстановления
обновлены только два существующих модуля нового runtime и добавлен один
DNS-модуль; образы прежние. SHA256 пакета:
`eca914ad4e44944eb47a503c5a950eda712e53d71bf653fca1338925e9d2e7e5`.
До и после совпали SHA256 основного Mihomo config, StartedAt и RestartCount
WireGuard/Mihomo. Перезапущена только новая maintenance-служба. Приёмочные
разрешения и Auto не включались.

Десятиминутное наблюдение завершено: **301 замер с шагом 2 секунды, 57 поколений
DNS-снимка, 0 просроченных**, source revision совпадал с новой схемой. Все
**21 проверка runtime** успешны, Docker-контракты не изменились, worker active.
Итоговый запрос с проверкой TLS через production-вход: YouTube HTTP200/209мс,
Discord HTTP200/366мс, Telegram HTTP200/497мс. Instagram вернул
`unknown/probe_failed`, без HTTP-ответа; это не успешная приёмка четвёртого сервиса.
Отчёт не заменяет проверки клиентского пути, восстановления и изоляции.

В ограниченном повторе Instagram через неизменённую `disorder-sni` получил
HTTP200 дважды (496 и 582 мс), DNS-адрес во время обеих проб не менялся.
Изолированный кандидат `disorder-1` также дал HTTP200/796мс, но **не применялся**.
Прямая проба и два других кандидата завершились `DockerError`: сравнение
неполное, ошибка инфраструктуры не приписывается стратегии. Selection-файл
не менялся, runtime после сравнения healthy. Один неуспех и два успеха — не
основание объявлять Instagram стабильным или разрешать Auto.

## Что ещё требуется

- Разобрать неуспех Instagram на новом DNS-контексте; не выдавать стабильный DNS
  за доказанную доступность всех четырёх сервисов.
- Уточнить стадию `DockerError` у отдельных изолированных проб; проверить,
  что суммарный лимит запуска контейнера и сетевой пробы даёт корректную
  диагностику на NAS, а не ложный отказ стратегии.
- Проверить стабильное DNS-renewal, истечение TTL, отказ от private/FakeIP,
  восстановление общего network namespace и изолированную смену одного сервиса.
- Проверить реальные HTTPS-запросы через вход новой пары с WG-клиента; наличие
  адреса `10.66.0.4` на ПК подтверждено, сама сквозная проба ещё не выполнена.
- Проверить backup/apply/verify/rollback на NAS и только затем разрешить Auto.
- Выложить страницу и подключить панель к закрытому Unix socket. Старые VLESS/HY2,
  их fallback и клиентская маршрутизация должны остаться неизменными.

Работа HTTPS-контрольных адресов не доказывает работу видео, звонков, всех CDN,
мобильных приложений или UDP. Широкие категории на этот runtime не назначались.
