## Почему выбран ByeDPI

NFQUEUE bind/config/unbind на NAS успешны. Отсутствие загруженного модуля само
по себе не использовалось как доказательство несовместимости.

Дополнительный read-only сбор подтвердил DSM 7.3.2-86009 Update 4, kernel
4.4.302+, x86_64. В стандартных каталогах/регистрациях/символах не обнаружены
`owner` и `CONNMARK`. Сами эти отрицательные наблюдения оставлены `unknown`
в диагностическом коллекторе: он не подменяет отсутствующий kernel config.

На ПК, не на NAS, загружен официальный
[GPL-архив Synology r1000, 7.3-86009](https://global.synologydownload.com/download/ToolChain/Synology%20NAS%20GPL%20Source/7.3-86009/r1000/linux-4.4.x.txz)
из [каталога Synology](https://archive.synology.com/download/ToolChain/Synology%20NAS%20GPL%20Source/7.3-86009).
Опубликованный MD5 совпал: `b11f535a04b82cb89e5cac4e8743f4f9`.
Зафиксированный SHA-256 архива:
`61065ab2d05befd4682d3a0fba4fac138dba32d1ad193d685bd924f0c01bdbf9`.

В `linux-4.4.x/synoconfigs/r1000`:

```text
CONFIG_NET_NS=y
CONFIG_SYNO_R1000=y
CONFIG_NETFILTER_NETLINK_QUEUE=m
CONFIG_NF_CONNTRACK_MARK=y
# CONFIG_NETFILTER_XT_CONNMARK is not set
# CONFIG_NETFILTER_XT_TARGET_CONNMARK is not set
# CONFIG_NETFILTER_XT_MATCH_CONNMARK is not set
# CONFIG_NETFILTER_XT_MATCH_OWNER is not set
```

Вывод ограничен согласованной схемой: штатная конфигурация этой платформы/сборки
не содержит owner/CONNMARK, необходимых для запланированного захвата двух
направлений Zapret2. Vendor config вместе с живой инвентаризацией обосновывает
выбор предусмотренной планом ветки **ByeDPI**, без установки нештатных модулей.
Это не утверждение, что все возможные варианты Zapret на Synology невозможны,
и не чтение точной конфигурации работающего ядра из отсутствующего `/proc/config.gz`.

Отчёт NAS: `netfilter-inventory-d1698c9626fd4397ab2cd96b0168ed32.json` в закрытом
каталоге `.vless-maintenance` существующего проекта. Модули не загружались.

## Что пока не доказано

- Обход DPI/работа конкретных сайтов и стриминга: внешняя сеть стенду недоступна.
- Совместимость с FakeIP/DNS основного Mihomo. Его DNS слушает 53; отдавать
  FakeIP системному resolver ByeDPI нельзя. В pinned Mihomo SOCKS сериализация
  сохраняет hostname при наличии `Host`, поэтому наличие `DstIP` само по себе
  не доказывает отсутствие стороннего DNS. В стенде `--no-domain`, только IPv4.
- UDP/QUIC, IPv6, автоподбор, pins и наблюдение настоящих клиентских сессий.
- Автовосстановление при пересоздании владельца namespace и запрет новых
  соединений после восстановления. `depends_on` не объявлен достаточной защитой.
- Длительная нагрузка, ресурсный baseline, интеграция backup/restore/worker,
  показ маршрута в публичной панели и Telegram.

`production_ready`, `dns_contract_verified`, `udp_verified`,
`dpi_bypass_verified`, `auto_strategy_verified` остаются `false`.
Проверка транспорта — часть задачи 2, не завершение всего anti-DPI этапа.
