## Защита DNS: проверенный ограниченный режим

Предыдущий автономный эксперимент разрешал домен дважды: сначала в авторизующем Mihomo, затем в ByeDPI. При изменении ответа DNS между запросами первая проверка адреса не защищала второе подключение.

В новой сборке для испытания используются точные домены и короткоживущий снимок проверенных публичных IPv4. Штатный `hosts` в [Mihomo v1.19.28](https://github.com/MetaCubeX/mihomo/blob/v1.19.28/tunnel/tunnel.go#L527-L535) передаёт нижнему SOCKS уже IP. ByeDPI всегда запускается с `--no-domain`; собственный DNS нового auth-прокси выключен. Поэтому повторного разрешения и петли через этот прокси нет. Старый mounted DNS-контракт v1 отклоняется.

Ограничения снимка: максимум 32 точных имени, 16 IPv4 на имя, срок не более десяти минут, только TCP/443. FakeIP, частные/служебные/зарезервированные адреса, IPv6, неизвестные цели и другие порты запрещены. При изменении/удалении/истечении снимка supervisor закрывает auth-прокси вместе с уже открытыми соединениями. В испытании сравнения используется ровно один одинаковый A-адрес для прямого и проксированного запроса.

На NAS проверено в отдельном namespace без внешней сети:

- По 262144 байта прошли через штатный авторизующий Mihomo в двух испытаниях.
- Нижний SOCKS получил только IPv4, не доменное имя: повторный DNS технически не выполнялся.
- Пять отрицательных целей в каждом испытании не передали данные.
- Изменение снимка и отдельно естественное истечение его срока закрыли существующий поток; auth завершился кодом 4.
- Все четыре временных контейнера удалены. ID/StartedAt/RestartCount пяти рабочих контейнеров, конфигурация основного Mihomo, firewall и маршруты совпали до/после.

Отчёт: `antidpi-pinned-75b09b21b19b4884b86343e35b71b36b.json`.

Это защита **ограниченного теста**, не готовое автоматическое обновление DNS для всех клиентских категорий. Для постоянного использования нужны безопасное продление снимков/контроль актуальности, согласование с правилами и DNS основного шлюза, scoped lifecycle и отдельная приёмка. Старый DNS/recovery-отчёт относится к предыдущему image ID; не выдаётся за проверку новой сборки.

- Пароль: `/volume1/docker/vpn-dashboard-maintenance/private/restic-password`, root:root, `0600`; родитель `0700`.
- Root-owned описание источников: `private/backup-sources.json`.
- Первый проверенный snapshot: `32e7eb434f460b0cdd281645c942c1a034ce244a686e20593edd5cf55211fb94`.
- Повторный snapshot с финальной проверкой неизвестных таблиц: `9c9876449ddb4af37e3b645511576738712f2f6845e8e8f73ea323e0160016b3`; run `94f7339550da46229bae2cf8e456fe19`, исходный архив `8fb0fb76c7c2676daf5d46654679d840728cae9e5a251bff39b6db129a0f4ab3`.

Сохранены 20 файлов: `wg-easy.db` и `wg0.conf` с существующими клиентами/серверной идентичностью, базы панели и Kuma, ключ шифрования панели, секрет controller, env/Compose, Mihomo config, шесть файлов правил, GeoIP/GeoSite и описание резервирования. SQLite копировались через online backup с WAL, не обычным копированием живых файлов.

Содержимое восстановлено только во временный закрытый каталог: сверены размеры/SHA-256 каждого файла, схемы и целостность трёх SQLite-баз. Затем прошёл `restic check --read-data`. Временные открытые копии удалены. Рабочие БД не заменялись, ключи клиентов не менялись.

Первый запуск остановился до секретов из-за унаследованного DSM ACL `0777+` на новом каталоге. Исправление затронуло только этот пустой root-owned каталог: снят унаследованный ACL, проверены `0700`. Никакие заполненные папки проектов или ACL GeoData не менялись.

Конфигурационные проекции сверяются до/после снимка; неизвестная таблица блокирует новый backup до review. Мониторинговые строки/сессии не считаются изменением настроек. Существующие production writers не останавливались: это не доказательство установленной глобальной блокировки обновлений или готового автоматического rollback.

Копия пока находится **на том же NAS**. Отдельного off-host экземпляра и переданной владельцу recovery-копии пароля ещё нет; потерю всего NAS эта схема пока не покрывает. Восстановление поверх действующих клиентов требует отдельного выбора snapshot и проверки более новых изменений.

## Реальные сайты

Проверки выполняются в новом namespace через обычный Docker bridge, без опубликованных портов. TLS-сертификаты проверяются. По три HTTPS-запроса к каждому сайту напрямую и через ByeDPI; не более 32 КиБ ответа, без входа в аккаунты, переходов по редиректам или видеопотоков. Секрет основного controller используется только существующей панелью для read-only DNS query и не передаётся новому runtime.

Первый внешний запуск `96c330bfb8e643b6bb2e5a53ef0e4dce`: Wikipedia дала HTTP 200 в 3/3 запросах обоими способами. YouTube и Discord не прошли TLS через текущую базовую стратегию `--split 1`; прямое соединение тоже не прошло TLS. DNS дал реальные публичные IPv4. Все три тестовых контейнера удалены, production/network/config до и после совпали.

Этот первый запуск использовал список A-адресов у proxy и первый A-адрес у direct. Поэтому результаты нельзя считать точным сравнением одного CDN-адреса. Добавлен регрессионный тест и повтор с одним и тем же закреплённым IP для обеих сторон; его результат фиксируется отдельно ниже.

`state=success` у harness означает, что измерения и cleanup выполнены, а не что обход работает. Решение о допуске сайтов хранится отдельно в `site_acceptance`; первый запуск получил `false`. Клиенты не подключаются по одному только зелёному состоянию контейнера.

Повтор `84bd538b307c4d1c99da6a92f10124a9` на одинаковых закреплённых адресах подтвердил результат:

| --- | --- | --- | --- |
| YouTube, `142.251.150.4` | 0/3 | 0/3 | TCP установлен, TLS timeout около 10 с |
| Discord, `162.159.128.233` | 0/3 | 0/3 | TCP установлен, TLS timeout около 10 с |
| Wikipedia, `208.80.154.224` | 3/3 HTTP 200 | 3/3 HTTP 200 | Через ByeDPI 637–646 мс |

Все 18 измерений завершились; три контейнера удалены, production/network/config совпали. Следовательно, DNS-цепочка и TCP-транспорт нового runtime работоспособны на контрольном сайте, но текущая стратегия обхода **не принята** для YouTube/Discord. Эти данные не доказывают единственную причину TLS-таймаута и не относятся к работоспособности двух действующих VPN-выходов. Следующий этап — ограниченный подбор стратегии на стенде, не переключение клиентов.

После review harness дополнительно печатает `SITE_ACCEPTANCE=failed` и возвращает код 2 при отрицательной приёмке сайтов (код 1 — ошибка самого измерения/cleanup). Это покрыто отдельным RED/GREEN тестом, чтобы завершившееся измерение не выглядело успешным обходом.
