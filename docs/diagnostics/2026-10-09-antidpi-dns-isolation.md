# Anti-DPI: изоляция соединений при обновлении DNS

Проверка 08–09.10.2026. Работа выполняется в текущем main, без агентов.
Этот отчёт не означает включение автоматической смены или маршрутизации клиентов.

## Реальные наблюдения до исправления

- С Windows/WireGuard `10.66.0.4` выполнены TLS-проверенные HTTPS-запросы
  через закрытый авторизованный SOCKS нового Anti-DPI. Первая серия: 12/12,
  повторная: 11/12; один TLS-сбой Discord, затем успешная следующая проба.
  YouTube, Telegram Web и Instagram во второй серии — по 3/3.
- Анонимный вход и неправильный пароль отвергаются. Запрещённый контрольный
  домен и FakeIP не дали HTTPS-ответа. Первоначальный отрицательный тест
  анонимного входа ошибочно повторял аутентификацию с паролем; его результат
  исключён, ошибка теста воспроизведена и исправлена перед повтором.
- Секрет SOCKS передан клиентской проверке в RSA-OAEP/SHA-256 конверте.
  Приватный ключ и расшифрованный секрет находились только в памяти процесса;
  публичный ключ/конверт на NAS после чтения удалены. В отчётах секретов нет.
- Зашифрованная копия перед приёмкой проверена фактическим восстановлением.
  Временно изменён только Instagram `disorder-sni → disorder-1 → disorder-sni`.
  Действительно заменён только его дочерний процесс; остальные три сохранены.
- Проверка остановки/восстановления контейнеров пока не выполнена: открытие
  контрольной TLS-сессии перед остановкой завершилось таймаутом. Остановка
  контейнеров не запускалась. Повторные read-only пробы показали закрытие TLS
  и краткую недоступность SOCKS-порта.
- Корреляция за 150 секунд: 274 замера, ни одного истёкшего DNS-снимка,
  **7 смен адреса Instagram и 7 замен общего auth-процесса**. В дискретных
  замерах 0,5 секунды порт был доступен; это не исключает более коротких пауз.

## Причина и границы исправления

`AuthService.tick()` останавливал общий Mihomo auth-процесс при смене адреса
любого одного сервиса. Поэтому обычная ротация Instagram обрывала также
соединения YouTube/Discord/Telegram. Это дефект нового Anti-DPI runtime,
не доказанная причина прежних обрывов VLESS/HY2.

Исправляется существующий runtime, а не состав Docker-проектов:

1. Auth-конфигурация предварительно валидируется и применяется через закрытый
   Unix-сокет в приватном `/tmp/auth` внутри auth-контейнера. Новый TCP-порт,
   Docker socket и доступ из панели к этому внутреннему API не появляются.
2. Требуется успешный ответ reload; потеря ответа не повторяет PUT, а закрывает
   неопределённое состояние. Истечение DNS и смена пароля сохраняют fail-closed.
3. При смене DNS заменяется только дочерний ByeDPI-процесс затронутого сервиса:
   его старые DNS-соединения закрываются, остальные обработчики не меняются.
4. Runtime-подтверждение содержит контекст DNS-адресов. Старое подтверждение
   не принимается за применение нового DNS. Простое продление того же адреса
   не вызывает замену процессов.

Подтверждение reload после применения проверено по
[исходнику Mihomo v1.19.28](https://github.com/MetaCubeX/mihomo/blob/v1.19.28/hub/route/configs.go#L374).
Это уточняет прежнее ограничение «без controller»: внешнего сетевого controller
по-прежнему нет; внутренний Unix-сокет доступен только в закрытом auth-контейнере.
Рабочий Mihomo, VLESS/HY2, WireGuard, DNS клиентов и их маршруты не изменяются.

## Проверка исправления

Локально наблюдались RED → GREEN для изоляции DNS, сохранения общего процесса,
подтверждения reload, потери ответа, ротации пароля и DNS-контекста подтверждения.
Полный deploy suite после дополнительных исправлений: 332 tests, один прежний
Linux-root skip. Python 3.8 AST: 34 модуля. Gitleaks: история, index и 377 файлов
рабочего дерева прошли проверку. Проверка авторская, без агентов; независимая
проверка не заявляется.

Отдельная контейнерная проверка на NAS без внешней сети выполнена на старом
и новом коде: старый разрывает SOCKS-поток к локальному echo-серверу при смене
адреса Instagram, новый сохраняет поток и PID общего auth-процесса.
Синтетические DNS-адреса этой проверки не доказывают доступ к реальным сайтам.

## Дополнительные ошибки восстановления на DSM

При пересоздании только `socks` установленный Compose передал Docker буквальное
`service:antidpi`; создание завершилось ошибкой `network service:antidpi not found`.
Шаблон новой пары использует `container:vpn-antidpi`, поддерживаемый
[Docker Compose](https://docs.docker.com/reference/compose-file/services/#network_mode).
Сохранена зависимость запуска, а проверка после пересоздания сравнивает также
фактический inode сетевого namespace. Рабочий проект `vpn-gateway` не изменён.

После исправления привязки контейнер работал, но его контракт не совпадал:
подтверждено, что изменился только порядок уникальных `Config.Env`. Хеширование
теперь канонизирует этот порядок; значения по-прежнему учитываются, а порядок
при дублирующихся именах не игнорируется. Регрессии наблюдались RED → GREEN.
При миграции прежний хеш сначала подтверждён перестановкой **тех же** значений;
произвольное новое состояние не объявлялось доверенным.

Перед каждым изменением создана и фактически восстановлена для проверки
зашифрованная копия. Ошибочные попытки сохранены отдельно; новый статус не
выдаётся за результат старой попытки. Установленная identity после исправлений:
`f9d168c10a93f401edaf1c04ca1ed1c1314df1ce9471b6002306a7c6a08f4f49`.

## Повторная живая проверка

- 150 секунд / 259 замеров: 8 изменений адреса Instagram, 8 замен только
  обработчика `1084`, **0 замен общего auth-процесса**, 0 просроченных DNS,
  0 недоступных SOCKS-listener в дискретных замерах.
- Windows/WireGuard `10.66.0.4`: **12/12** TLS-проверенных HTTPS/HTTP 200,
  266–672 мс на SOCKS + TLS + получение заголовков. Это не ICMP ping.
- Анонимный вход и неверный пароль отклонены; запрещённый домен и FakeIP
  не дали HTTPS-ответа. Секреты не сохранялись в отчёт.
- Первая клиентская серия после исправления включала повторную загрузку
  сертификатов Windows в лимит каждого запроса и дала 10/12. Эти времена
  нельзя считать чистой сетевой задержкой. Измеритель исправлен (RED → GREEN),
  TLS-контекст загружен один раз до сетевых таймеров, прежний отчёт сохранён.
- Отдельно native Python/OpenSSL 3.0.9 самого NAS получил TLS timeout на
  YouTube/Discord, но успешно установил TLS к Telegram/Instagram за 259/388 мс.
  Это другой клиентский TLS-путь; точная причина различия пока не доказана.
  Он не отменяет успешный Windows-клиентский тест и не скрывается из отчёта.
- Изоляция смены/отката Instagram на установленной identity подтверждена.
  Первая попытка lifecycle-теста остановилась до остановки контейнера из-за
  native NAS TLS timeout. Повторная через контрольный Telegram **успешна**:
  старое соединение закрыто, новые не прошли, после запуска владельца namespace
  штатный worker пересоздал зависимый SOCKS и восстановил здоровое состояние.
- Отдельно остановлен только новый DNS/maintenance-worker. После фактического
  истечения оставшихся 41,9 секунды lease все четыре обработчика закрылись,
  существующая TLS-сессия завершилась, runtime перестал считаться готовым.
  После запуска worker DNS и runtime восстановились без пересоздания контейнеров;
  выбор стратегий, политики, основной VPN и его конфигурация сохранены.
  Внешняя writer-блокировка освобождена до старта worker и осталась свободной.

Root-owned receipts: `antidpi-runtime-acceptance-20261009-v2.json` и
`antidpi-dns-expiry-20261009-v1.json`. Все проверки в этих двух квитанциях истинны;
предыдущие неудачные попытки не переписаны. Клиентский отчёт без секретов имеет
SHA-256 `c69052b68c147010351a64fa3d4921e3f3380f4be918273a0715ec84fe46a558`.

Auto остаётся выключен. Рабочие WireGuard/Mihomo, клиентские маршруты и ключи
не изменялись. Видео, звонки и UDP этими HTTPS-пробами не проверены.

## Подключение панели

Штатный production-измеритель worker после восстановления получил 4/4 HTTP 200:
YouTube 210 мс, Discord 205 мс, Telegram 331 мс, Instagram 551 мс. На основе
свежих identity-bound квитанций и хеша клиентского отчёта записаны шесть gates
готовности. Это не разрешение автополитики и не поддельный owner-grant.

В отдельном контейнере текущего образа dashboard, без сети и под UID10001,
подтверждены IPC-доступ, строгая схема четырёх сервисов и acquire/release общей
writer-блокировки. На Linux отдельно проверены права каталога сокета 0750,
владелец root:10001, сохранение inode при повторной подготовке и отказ для
symlink/чужого владельца.

read-only bind `/run/vpn-maintenance` и `MAINTENANCE_ENABLED=true`. Docker socket,
приватная база и секреты worker не переданы. Пересоздан только dashboard с тем же
image ID: ready200, запрос стратегий без входа401, четыре сервиса доступны через
IPC. Все остальные проверенные контейнеры сохранили ID/StartedAt/RestartCount;
SHA основного Mihomo и ревизия политик не изменились.

уже работающего dashboard, `running/healthy` и успешный запуск установленного
