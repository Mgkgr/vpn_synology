# Стратегии ByeDPI: проверки и автосмена

## Статус поставки

08.10.2026 в исходниках реализованы хранение политик, алгоритм автосмены,
расписание, протокол заданий, API и страница `/routes/antidpi/strategies`.
Это **не означает, что автоматика включена на NAS**. Текущие VLESS/Hysteria2,
WireGuard, DNS клиентов и правила не изменены.

При read-only проверке NAS панель была `running`, Docker server — `24.0.2`.
Сокет `/run/vpn-maintenance/control.sock` и новый модуль стратегий не были
видимы через текущего SSH-пользователя (`absent_or_inaccessible`); отсутствие
прав на каталог не выдаётся за доказанное отсутствие файла.

Пока нет установленного постоянного исполнителя с проверенным production-адаптером,
страница показывает недоступность, а управление блокируется. Сейчас в репозитории
есть тестируемая граница такого адаптера, **но не готовый адаптер применения
стратегий к производственным контейнерам**. Подмена его фикстурой запрещена.

## Поведение

- Четыре фиксированных HTTPS-сайта: YouTube, Discord, Telegram Web, Instagram.
  Проверяется TCP/443 с TLS. Видео, звонки, мобильное приложение и UDP этой
  проверкой не подтверждаются.
- Проверка текущей стратегии — раз в 30 минут; доступны 5/15/30/60 минут.
  Первичный отказ обнаруживается в пределах этого интервала, не мгновенно.
- Суточный набор — 05:30 `Asia/Yekaterinburg`: текущая + до двух альтернатив.
  Ручной полный подбор — закрытый каталог, максимум 60 попыток / 20 минут.
- Автосмена: три транспортных отказа через 30 секунд; затем три успеха
  кандидата через 10 секунд на том же DNS-контексте и повторная проверка текущей.
  Если текущая восстановилась, смены нет.
- Ошибки DNS/инфраструктуры/сертификата, HTTP 403/429/5xx, старые данные и
  неверное время не запускают ротацию. Транспортный отказ не доказывает DPI.
- Между автосменами минимум 15 минут, максимум две в час на сервис.
  Ограничения сохраняются в SQLite. Исправная новая стратегия не меняется обратно.
- `Закреплена` запрещает автосмену. Ручной подбор ничего не применяет и
  не пополняет серию автоматических отказов. Выбор в списке — только черновик.
- Обычный администратор читает. Изменения и ручные проверки используют уже
  существующее подтверждение владельца, привязанное к конкретной операции.
  Автоматические задания используют сохранённую политику, не пароль.

## Страница

Переход: «Маршруты → Anti-DPI: стратегии, проверки и автосмена».
Для сервиса отдельно показаны текущая стратегия, режим, время/результат пробы,
задержка, количество успешных последних попыток и начало серии отказов.

Кнопки «Проверить сейчас» и «Подобрать» не меняют выбор. «Проверить и применить»
сначала проверяет выбранный вариант; режим после применения выбирается явно.
Расписание, история смен и попытки раскрываются внутри карточки.

ID задания сохраняется в адресной строке. Потерянный ответ проверяется по тому же
ID без повторного POST. Закрытие страницы не отменяет job. Отмена возможна до
этапа применения; прерванный неопределённый job блокирует новые изменения до сверки.

Статус «подтверждение устарело» означает, что данных недостаточно **для смены**;
он не доказывает отказ сервиса между регулярными проверками. Сохранённая дата
проверки остаётся видна. Успешный откат конфигурации не означает восстановление
работы прежней стратегии.

## Граница исполнителя

`StrategyStore` использует root-owned SQLite `JobStore`, тот же mutation-lock,
постоянные ревизии и журнал эффектов. Владелец политики фиксирован текущей
идентичностью сборки/каталога. Изменение каталога или runtime отзывает автополитику.
Только host-код вправе вызывать `register` и создавать автоматические задания;
клиент не может задавать их тип, команды, URL, пути или параметры запуска движка.

`MaintenanceService(..., strategies=runner)` обслуживает безопасные снимки и
задания. `StrategySchedule.tick(now)` выдаёт не более одного job, с очередью
до одной записи на сервис; host loop передаёт ID в `StrategyRunner.run`.
Перезапуск сначала вызывает `JobStore.recover_after_restart`, не повторяет
неопределённое применение. Сам HTTP GET не вызывает `tick`, Docker или сетевые пробы.

Будущий host-адаптер обязан реализовать:

1. `capabilities()` — только кешированные доказательства готовности, не фиктивный
   `True`; `comparison_context(service)` — свежий проверенный DNS-снимок,
   fingerprint версии/каталога и успешный DIRECT HTTPS-контроль Wikipedia.
2. `probe(service, strategy, context, timeout)` — изолированное тестовое окружение,
   только проверенный публичный IPv4, неизменный SNI, TLS, без redirect, до
   10 секунд / 32 KiB; исключение или неизвестный формат означает `unknown`.
3. `backup(selections, expected_revision)` — зашифрованная и проверенная копия;
   закрытый token не уходит в API. До мутации проверяется полная новая конфигурация.
4. `apply(selections, expected_revision, token)` — CAS runtime непосредственно
   перед атомарной записью; изменяется только выбранный сервис Anti-DPI.
5. `verify(service, context, timeout)` — запрос через реальный производственный
   вход, не повтор тестового контейнера. `rollback(token, expected_revision)`
   возвращает `True` только после доказанного возврата своей конфигурации,
   не перезаписывая более новую ревизию.

До выдачи `apply_ready` ещё обязательны постоянное безопасное обновление DNS,
восстановление namespace после рестарта, отдельные стратегии сервисов на
закреплённом движке и сквозная приёмка с одним WireGuard-клиентом. Эти зависимости
относятся к незавершённым задачам 2/3/7 прежнего anti-DPI-плана.

Наблюдения: до 30 дней и 50000 строк; изменения: до 90 дней. Политики и
закрепления очисткой не удаляются. SQLite, секреты, backup и runtime-файлы в Git
не публикуются.

## Проверки разработчика

Тесты `deploy/tests/test_strategy_*.py` проверяют решения, отказы и восстановление
на реальном SQLite с детерминированным тестовым транспортом. Это не испытание
блокировок реального провайдера. `backend/tests/test_antidpi_api.py` проверяет
настоящие сессии, CSRF, owner-grants, потерю ответа и закрытые схемы.
Frontend-тесты проверяют черновик/активную стратегию, права, расписание и повторы.
Браузерная проверка выполняется отдельно на локальных фикстурах, без изменений NAS.
