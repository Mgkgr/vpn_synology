# Третий anti-DPI-выход и Telegram-оповещения

Дата: 27.09.2026. Статус: исходная письменная спецификация утверждена пользователем 27.09.2026. Дополнение «Управление стратегиями anti-DPI» и уточнения реализации ожидают проверки обновлённой спецификации. Пользователь уточнил, что общий перезапуск касается только VPN-комплекса, не NAS; управление обслуживанием описано отдельно в `2026-09-27-component-maintenance-design.md`. Это описание будущих изменений, не отчёт об установленном сервисе.

## Цель и границы

Добавить для существующих WireGuard-клиентов отдельное направление anti-DPI на Synology DS923+ и оповещения в Telegram о длительной недоступности каждого выхода. Не менять клиентские профили, их ключи, работающие DIRECT-исключения, порядок основного/резервного VPN или настройки роутеров.

Текущие технические ID сохраняются: `WG-IMP` отображается как `VLESS-NL`, `HY2-USA` — как `HY2-DE`. Название HY2 соответствует профилю провайдера, а не подтверждённой географии IP. Новый ID — `ANTIDPI`; отображение указывает фактический движок: `Zapret2` либо `ByeDPI`, без подмены названий.

Anti-DPI не даёт зарубежный IP и не является равноценной заменой VPN. Он не добавляется в `VPS-FALLBACK`. При его отказе правила не должны незаметно превращаться в обычный DIRECT. Автоматический переход между anti-DPI и VPN не входит в первый релиз.

## Выбор движка и проверка NAS

Предпочтителен официальный `bol-van/zapret2`, `nfqws2`, с отдельным SOCKS5-сервером HevSocks5Server. Mihomo направляет в него только трафик явно назначенных правил. Альтернатива — официальный `hufrea/byedpi`, уже являющийся SOCKS-прокси. Установщик Z2K для Keenetic/Entware не используется; `tpws` из завершившего развитие Zapret 1 не выбирается для новой долгосрочной конфигурации.

Решение принимается по проверке:

1. Без изменения системы прочитать архитектуру, версию ядра, доступные модули и параметры сборки NFQUEUE. Отсутствие загруженного модуля само по себе не доказывает отсутствие поддержки.
2. Если NFQUEUE подтверждён, после отдельного согласования пробного запуска проверить привязку очереди в изолированном сетевом окружении. Не загружать модули ядра, не менять firewall DSM и не устанавливать сторонние `.ko` автоматически.
3. Если поддержки нет — выбрать ByeDPI. Если NAS недоступен или результат неоднозначен — оставить выбор неподтверждённым и не объявлять Zapret2 несовместимым без доказательств.
4. Возможности UDP/QUIC включать в карточке только после сквозного испытания выбранного движка; поддержка SOCKS UDP сама по себе не подтверждает обход DPI.

Фактическая проверка 27.09.2026 в 17:32 UTC+5: имя NAS разрешается в `91.203.237.227`; локальный и публичный адреса маршрутизируются через OpenVPN. SSH к `192.168.2.103:5004` завершился таймаутом. NFQUEUE пока не проверен. Изменение маршрутов Windows не является частью установки и требует отдельного разрешения.

## Изоляция и маршрутизация

Добавляется отдельный сервис/пара контейнеров `antidpi`, не разделяющий сетевой namespace WireGuard/Mihomo. Для Zapret2 SOCKS-сервер и обработчик пакетов разделяют только собственный namespace. У ByeDPI нет встроенной авторизации SOCKS: для него используется отдельный вход Mihomo с авторизацией, единственным выходом в ByeDPI на loopback и без TUN, controller, системного DNS-перехвата или запасного DIRECT. Это отдельный экземпляр, не изменение назначения основного Mihomo. Образы и исходники фиксируются по версии/commit и digest, обновляются вручную с откатом.

- SOCKS-порт доступен только внутри Docker-сети, не публикуется в LAN/WAN; используется отдельная учётная запись. Секрет хранится вне Git.
- Без `network_mode: host`, Docker socket и `privileged`. Для nfqws2 допускаются только необходимые `NET_ADMIN`/`NET_RAW` в его namespace; ByeDPI запускается с минимальными правами.
- Правила перехвата ограничены соединениями SOCKS-сервера внутри нового namespace. Для автоподбора наблюдаются как исходящие пакеты, так и относящиеся к этим соединениям ответы: без входящего направления нельзя достоверно обнаруживать часть отказов. DSM, другие контейнеры, оба VPN и обычный DIRECT не затрагиваются.
- Готовность требует SOCKS-соединения и работающего обработчика. Очередь NFQUEUE для обрабатываемого трафика настраивается без `queue-bypass`: исчезновение обработчика не должно пропускать этот трафик без обработки. При остановке nfqws2 SOCKS-сервис перестаёт принимать новые запросы; никакой тихой выдачи обычного DIRECT. Приёмка проверяет и уже открытые соединения.
- Сохраняется DNS-политика Mihomo. FakeIP-адреса не должны передаваться как реальные назначения; запрещены DNS-петли и самовольная замена системного DNS NAS.

В Mihomo добавляются SOCKS5-выход `ANTIDPI`, file-provider `managed-antidpi` и правило для этого provider после существующих DIRECT-исключений, перед более общими VPN-категориями. Пустой provider не меняет текущую маршрутизацию. Явные конфликты категорий показываются в интерфейсе; сохраняется порядок «DIRECT → ANTIDPI → закреплённые VPN → автоматический VPN».

Первое включение — только для согласованных тестовых доменов. Массовое назначение категорий не выполняется вместе с установкой. Подбор стратегий производится на нашем провайдере; готовая стратегия из другого проекта не считается проверенной. Существующие ограничения UDP/443 для отдельных клиентов не отменяются автоматически.

## Интеграция панели

Текущий код явно ограничен двумя выходами в схемах API, collector и правилах. Добавляется общий реестр выходов, но состав `VPS-FALLBACK` остаётся отдельно зафиксированным из двух элементов.

- «Обзор»: третья карточка, движок, последнее наблюдение, длительность отказа, состояния «работает», «частично», «проверяем», «недоступен», «нет данных».
- «Маршруты»: отдельная ветка anti-DPI, независимые пробы и «Проверить сейчас»; выбор карточки не переключает трафик.
- «Правила»: действие `ANTIDPI` для поддерживаемых доменов и категорий. Оно доступно только после регистрации и готовности выхода.
- «Журнал»: пробы, изменения состояния, начало/конец инцидентов, состояние передачи уведомлений. В пробе отдельно записываются проверяемый выход и выбранный fallback — это не одно поле.

История старых ID, учёт трафика клиентов, существующие права администратора и защита публичной панели сохраняются. Добавление третьего выхода не расширяет разрешённые пользовательские URL или доступ к приватным адресам для проверок.

## Управление стратегиями anti-DPI

Пользователь хочет видеть текущий автоматический выбор и управлять настройками из нашей панели. Это выбор стратегии обработки трафика, не VPN-сервера. WARP и другие дополнительные туннели из сторонних сборок не добавляются этим расширением. Автоподбор не меняет `VPS-FALLBACK`, правила DIRECT или перечень доменов, направляемых в ANTIDPI.

Вкладка «Стратегии» находится внутри anti-DPI, отдельно от управления VLESS/HY2:

- Таблица только для обрабатываемых ANTIDPI доменов: домен, профиль TCP/UDP, режим «Авто» или «Закреплён», текущая стратегия и версия набора, последнее наблюдение, последний подтверждённый успех, время и причина смены. Неизвестный hostname не подменяется вымышленным именем; состояние по IP явно подписывается.
- «Выбрать стратегию», «Закрепить», «Вернуть авто», «Сбросить подбор для домена». Закрепление запрещает автоматическую ротацию именно выбранной записи. При неуспехе она остаётся закреплённой, получает предупреждение и не переключается молча в DIRECT.
- «Подобрать» запускает ограниченный по времени/числу попыток тест заданного публичного домена в отдельном тестовом окружении. Видны этап, проверенный протокол, результаты кандидатов и фактическая длительность. Закрытие страницы не прерывает задание. Отмена останавливает пробы и очищает только тестовые ресурсы. Результат сам по себе не применяется к клиентам: отдельная кнопка «Применить».
- Отдельные «Проверить настройки», «Применить» и «Вернуть предыдущие». Перед применением валидируется вся получившаяся конфигурация; ошибка оставляет рабочую версию нетронутой. Показывается необходимость краткого перезапуска только anti-DPI и перечень затрагиваемых профилей. Запуск нескольких взаимоисключающих операций блокируется.
- Простые настройки: разрешённый набор стратегий, порог неудач, окно подсчёта, таймаут проб, списки доменов и исключений. Расширенные настройки — типизированные разрешённые параметры проверенных стратегий. Нет произвольных shell-команд, путей к файлам, `lua-init`, пользовательского Lua или строк, исполняемых через shell.

Для Zapret2 адаптируется штатная логика `circular` и детекторы из `zapret-auto.lua`; не создаётся параллельный конкурирующий алгоритм переключения. Исходящие и входящие наблюдения должны относиться к тем же соединениям нового сервиса. Повтор одного события не увеличивает счётчик несколько раз. Причины вида RST/ретрансляций показываются как признаки неудачи, а не как доказательство DPI. Успех общего HTTPS-теста не подтверждает работу всего приложения.

Автоматический режим перебирает только предварительно проверенный набор. Полный перебор стратегий по расписанию или при каждом открытии страницы не запускается. Первый релиз хранит до 1000 автоматически наблюдаемых записей, удаляя записи без наблюдений за 30 дней и самые старые при достижении лимита; до 128 закреплённых настроек хранятся отдельно и удаляются только явным действием. При достижении лимита закреплений новое не создаётся молча. Сохраняются выбор, режим и версия набора; после перезапуска выбранная стратегия восстанавливается только при совместимости с установленным движком/набором. Несовместимость видна как «требуется повторная проверка», а не как подтверждённая работоспособность.

Ручной подбор ограничен одним заданием одновременно, одним проверяемым публичным доменом, 60 попытками и 20 минутами, что наступит раньше; отдельная попытка имеет конечный таймаут. Частичный результат сохраняется с отметкой причины остановки, а не выдаётся за проверку всего набора. Автоматическая оценка по признакам трафика и результат явной контрольной пробы имеют отдельные отметки источника и времени.

Списки ANTIDPI уточняют обработку только уже направленного сюда трафика. Добавление в них не создаёт скрытые правила Mihomo и не отменяет DIRECT. При конфликте интерфейс показывает, какое существующее правило не даст трафику попасть в anti-DPI. Автоматическое расширение маршрутизации по всему LAN выключено и не входит в релиз.

Возможности UI зависят от реально установленного движка и версии. Если выбран ByeDPI, показываются только проверенные и реализованные для него настройки; совместимость автоподбора/закрепления Zapret2 не предполагается. Неподдерживаемая функция явно обозначается, не имитируется. То же касается UDP/QUIC. Внешняя телеметрия и Keenetic-специфичные установщики Z2K не переносятся.

История стратегий содержит время, профиль, выбранный вариант, безопасный код причины и инициатора ручного изменения. Не сохраняются тела пакетов, полные URL, токены или клиентские ключи. Домены из этой истории не отправляются автоматически в Telegram. Секреты SOCKS отсутствуют в API, предпросмотре и журналах.

Приёмка: ротация только незакреплённого домена; сохранение выбора после рестарта; отсутствие входящих наблюдений выявляется как неполная диагностика; неверные параметры не применяются; параллельная правка не перезаписывается; тестовый подбор не влияет на работающие клиенты; отмена и возврат предыдущей конфигурации проверены. Изменение версии движка/набора инвалидирует прежнее свидетельство сквозной проверки до повторной приёмки.

## Достоверное определение отказа

Для оповещений используются отдельные контрольные пробы, а не произвольный список сайтов администратора и не факт выбора fallback. Базовый набор: Cloudflare `generate_204`, Google `generate_204`, GitHub API. Проверка конкретного сайта/приложения остаётся отдельной диагностикой.

Уточнение реализации: `/proxies/{name}/delay` изменяет историю доступности проверяемого объекта Mihomo. Для новых контрольных проб создаются скрытые диагностические группы `DASH-HEALTH-<ID>` типа `select`, каждая ровно с одним соответствующим выходом, без своего периодического health-check и без DIRECT. Запрашивается именно `/proxies/<группа>/delay`, не групповой тест её участников. На изолированном экземпляре проверяется, что истории рабочих выходов и выбор `VPS-FALLBACK` не меняются из-за таких проб. В production мониторинг включается только после этой проверки.

- Цикл раз в 60 секунд, до трёх параллельных запросов, таймаут пробы 10 секунд; циклы не перекрываются. Три выхода дают максимум девять вызовов контрольных проб в минуту. Сам Mihomo при включённом `unified-delay` может сделать повторный короткий HTTP-запрос внутри одной пробы; это учитывается при измерении нагрузки.
- При исправном controller цикл успешен, если прошли минимум две из трёх контрольных HTTPS-проб. Одна ошибка означает частичный сбой, не полный отказ.
- Если две или три пробы не проходят непрерывно 600 секунд, создаётся подтверждённый инцидент. Интервал считается от первой неудачной завершённой пробы; точное физическое время начала сбоя неизвестно.
- Восстановление — два последовательных успешных цикла. Единичный успех не закрывает уже подтверждённый инцидент.
- Ошибка доступа к controller, пропущенные циклы или отсутствие наблюдений более 180 секунд означают «нет данных». Не создаётся выдуманный отказ всех выходов. Неподтверждённая серия сбрасывается; существующий инцидент остаётся открытым до новых успешных проверок.
- Состояние, временные отметки и идентификатор инцидента сохраняются в SQLite. Перезапуск панели не создаёт второй инцидент и не считается восстановлением.

Для anti-DPI дополнительно хранятся результаты согласованных целевых сервисов. Зелёные общие контрольные адреса показывают доступность транспорта, но не доказывают обход блокировки каждого сервиса. Неудача целевого сервиса выводится как отдельная проблема сервиса, а не как общий отказ маршрута.

## Telegram через существующий Uptime Kuma

Используется штатная Telegram-интеграция установленной версии Kuma и её Push API. Новый самостоятельный бот-сервис и команды управления VPN в первом релизе не нужны. Для каждого выхода создаётся отдельный push-monitor, плюс heartbeat работоспособности collector. Десятиминутное подтверждение выполняет панель; второй такой задержки в Kuma нет.

Панель передаёт короткий безопасный статус раз в минуту. Временная недоступность controller не меняет последнее подтверждённое состояние инцидента и отмечается отдельным монитором наблюдения. Если heartbeat полностью исчез, сообщение Kuma должно говорить «нет данных мониторинга», а не «подтверждён отказ VPN». Возврат данных после такого разрыва не выдаётся за восстановление выхода без контрольных проб. До первой достоверной пробы выход показан как непроверенный.

Сообщения: подтверждённый отказ с временем первого наблюдения, повтор при продолжающемся отказе не чаще раза в час, восстановление с длительностью инцидента. Указывается, какой выход проверялся и какой выбран fallback. Ручная кнопка диагностики не увеличивает частоту напоминаний. Не передаются ключи, IP клиентов, история посещений, полные URL с параметрами или тексты необработанных исключений.

Точность интервала напоминаний и обработка пропавшего heartbeat проверяются на установленной версии Kuma: `resendInterval` может измеряться количеством heartbeat, а не секундами. Привязка делается к минутному publisher, а не к числу пользовательских проверок. При временной недоступности Kuma последнее состояние ожидает повторной передачи с ограниченной задержкой; интерфейс различает «передано Kuma» и «доставлено в Telegram» — первое не доказывает второе. Во время наладки используется отдельный тестовый монитор.

Токен создаётся пользователем в BotFather и вводится в защищённую настройку Kuma; пользователь запускает бота или добавляет его в нужный чат. Не сохранять токен в исходниках, аргументах процессов и логах. Push-токены панели — отдельные файлы `0600`; данные Kuma закрываются файловыми правами и включаются в зашифрованный backup. Нельзя обещать, что сама база Kuma шифрует Telegram-токен.

Kuma остаётся вне namespace проверяемых VPN. Доступ к Telegram проверяется отдельно. Если Telegram недоступен с NAS либо отключён весь NAS/интернет, мгновенная доставка не гарантируется. Внешний наблюдатель за NAS — отдельная задача и в первый релиз не входит.

## Развёртывание, проверка и откат

Перед изменениями — зашифрованные проверяемые копии конфигурации Mihomo, правил, базы панели и Kuma. Перед записью повторно сверяются хеш/ревизия исходного состояния; параллельные изменения администратора не перезаписываются. Миграции базы только добавляют новые таблицы/поля. Не делать `compose down`, не перевыпускать WireGuard-профили и не отключать рабочие VPN для имитации отказа.

Сначала изолированный тест anti-DPI, затем регистрация пустого provider, затем точечное тестовое правило и только после сквозной проверки — возможность назначения категорий. Проверяются TCP, разрешённый UDP/QUIC, DNS/FakeIP, приложение на реальном клиенте, обычный DIRECT и оба прежних выхода. Остановка нового обработчика испытывается только на тестовом трафике. Нагрузка сравнивается с исходной, без обещаний скорости до измерений.

Автотесты: три выхода и прежние ID; границы 599/600 секунд; единичный сбой; две успешные проверки для восстановления; stale/unknown; перезапуск процесса; отсутствие дублей; ошибки Kuma; отсутствие секретов в ответах/логах. Интеграционные тесты не должны отключать production-выходы. Для Telegram подтверждается получение реального тестового сообщения пользователем.

Откат восстанавливает только изменённые конфигурации/правила и совместимую версию панели, отключает новый сервис и новые мониторы. База клиентов, ключи и остальные проекты остаются нетронутыми. Развёртывание не считается завершённым до проверки сохранения результата после перезапуска только новых компонентов.
