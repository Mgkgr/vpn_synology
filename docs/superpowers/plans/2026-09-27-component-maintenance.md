# Обслуживание VPN-комплекса — план реализации

> **For agentic workers:** REQUIRED SUB-SKILL: `superpowers:executing-plans`. Выполнять задачи с отметками `- [ ]` самостоятельно в текущей сессии, без агентов — выбор пользователя. Спецификация утверждена; план ожидает проверки. Не запускать обновление или рестарт production в рамках написания кода.

**Goal:** показывать версии компонентов и безопасно выполнять подтверждённые обновления, откат и упорядоченный перезапуск только VPN-комплекса из панели.

**Architecture:** root-owned исполнитель на NAS с постоянным журналом заданий, закрытым Unix socket и фиксированным каталогом компонентов. Публичный backend проверяет владельца/повторный пароль и передаёт только типизированные задания; Docker socket в контейнер не монтируется. Исполнитель переживает рестарт dashboard и сверяет фактическое состояние перед продолжением прерванной операции.

**Tech Stack:** Python 3.8 stdlib для исполнителя NAS; существующие Python 3.12/FastAPI/SQLAlchemy/httpx и React/React Query для панели; Docker Compose, SQLite, существующий Restic. Без нового стороннего root-installer, Watchtower и обязательного нового пакета Python на NAS.

**Spec:** `docs/superpowers/specs/2026-09-27-component-maintenance-design.md`; стратегиям посвящён `docs/superpowers/specs/2026-09-27-antidpi-telegram-design.md`.

## Global Constraints

- Только основной Mihomo, wg-easy/WireGuard, Kuma, MetaCubeXD, dashboard и установленный anti-DPI с зависимостями. Не NAS, Docker daemon, роутеры или другие проекты.
- Обновление только по подтверждению, закреплённая версия/digest; проверка наличия релизов раз в сутки в 05:00 по времени NAS и вручную. Предрелизы по умолчанию скрыты.
- Изменения компонентов — только владелец после повторного пароля; разрешение одноразовое, действительно пять минут, связано с сессией и точными параметрами. Остальные администраторы видят состояния/историю; прежние права на клиентов/правила не расширяются и не отбираются.
- Одно изменяющее задание одновременно. Повтор запроса возвращает тот же job ID. Нет произвольных команд, путей, URL, image name или YAML из браузера.
- Проверяемый зашифрованный согласованный backup до замены. Откат — совместимый образ/конфигурация/БД; не восстанавливать старую БД поверх новых изменений без отдельного подтверждения потери данных.
- Окно обслуживания: 15 минут restart, 30 минут update-очередь, без автоматического продления; начинается перед первым воздействием. Истечение окна не убивает миграцию.
- Порядок: Mihomo останавливается перед WireGuard, WireGuard запускается первым; внутренние зависимости anti-DPI проверяются отдельно; dashboard перезапускается последним.
- Исходно отключённый сервис не включать без явного выбора. Каждому временно остановленному сервису — не более одной попытки восстановления. Нет `compose down`, prune, удаления volumes или фонового цикла рестартов.
- Все секреты вне Git/лога/argv, права `0600`; UTF-8, shell LF, PowerShell 5.1. Не добавлять NanoCPUs на DSM с неподдерживаемым CFS.

## Review Focus

1. У дополнительного администратора тоже есть `owner_id`: это не доказательство владения. Задача 3 проверяет `principal.username` и актуальную запись владельца.
2. Dashboard отключился после принятия задания, но до ответа: повтор не должен ещё раз менять контейнер. Задачи 2, 5 проверяют persisted job ID и восстановление статуса.
3. После успешной миграции уже создан новый WG-клиент: откат базы не может стереть его автоматически. Задача 4 проверяет блокировку writer, ревизию и отдельное подтверждение потери данных.
4. Compose/образ/namespace изменён вручную либо каталог релизов подменён: совпадения имени контейнера недостаточно. Задачи 1, 2, 4 проверяют labels, доверенный источник, digest и исходную ревизию.
5. Окно обслуживания истекло, а процесс завис или NAS выключился: не оставлять вечное заглушение уведомлений и не повторять стадию вслепую. Задачи 2, 5, 6.

## Файлы и порядок выполнения

`deploy/maintenance/` — небольшой пакет исполнителя: `catalog.py`, `releases.py`, `protocol.py`, `store.py`, `service.py`, `docker_adapter.py`, `backups.py`, `restart.py`, `updates.py`, `readiness.py`. Они отвечают соответственно за фиксированный каталог, проверку релизов, закрытый протокол, журнал, координацию, ограниченные Docker-вызовы, снимки, restart, update/rollback и проверки связи. `components.json` содержит доверенные источники/сервисы, не секреты. Не переносить весь существующий deploy в новый framework.

Backend: новые `maintenance_client.py`, `maintenance_auth.py`, `maintenance_api.py`. Frontend: `ComponentsPage.tsx` и `MaintenanceJobPanel.tsx`. Большие существующие `routes.py`/страницы меняются только в точках подключения.

Выполнить локальные задачи 1–5 плана health, затем задачи 1–5 этого плана, затем задачи 1–6 anti-DPI. Read-only preflight anti-DPI можно выполнить раньше независимо от этого порядка. Live-стадии каждого плана согласуются отдельно; недоступность NAS или неподтверждённый движок не мешают тестам maintenance без anti-DPI. После подтверждения установки anti-DPI его адаптер подключается к уже проверенным контрактам, не создаёт второго root-worker.

Проверки из корня: `.\backend\.venv\Scripts\python.exe -m unittest discover -s deploy/tests -p 'test_maintenance*.py'`. Из `backend`: `.\.venv\Scripts\python.exe -m pytest tests/test_maintenance_client.py tests/test_maintenance_auth.py tests/test_maintenance_api.py -q`. Из `frontend`: `npm run test -- --run`, `npm run build`. Тестовые subprocess/Docker/сеть заменены адаптерами; локальные тесты не запускают NAS-команды.

## Согласованные ограничения первого релиза

Новые upstream-релизы отображаются автоматически; установка предлагается только после проверки конкретного артефакта/миграции и включения в root-owned список. Это не универсальная кнопка установки любого latest. Смена Zapret2↔ByeDPI — отдельная миграция. При недоступности всего NAS Telegram с этого же NAS не гарантируется. Инструкции для обновления доверенного каталога и локального status/recovery входят в `docs/component-maintenance.md`.

Основание для adapter gate: [штатный Telegram provider Kuma 2.3.2](https://github.com/louislam/uptime-kuma/blob/2.3.2/server/notification-providers/telegram.js). Его вызов — version-pinned внутренняя интеграция, не обещание стабильного публичного API.
