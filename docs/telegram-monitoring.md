# Telegram-оповещения через существующий Uptime Kuma

Статус на 04.10.2026: код collector/publisher и локальные тесты есть. Пользователь выбрал существующего бота `@greece_bank_bot`. **Подтверждённой доставки Telegram нет; это инструкция следующего этапа, не отчёт об активации.**

## Перед настройкой

- Нужны токен бота и конкретный получатель (личный чат/группа, при необходимости тема). Username бота не заменяет ни токен, ни Chat ID. Токен вводит владелец только в закрытую форму Kuma, не в чат, Git, аргументы команд или диагностические отчёты.
- Сначала обеспечить проверенное HTTPS-подключение к Kuma либо разрешённый SSH-туннель. Известный `192.168.2.103:3001` использует HTTP. Попытка локального туннеля 04.10 отклонена SSH-сервером; его настройки не менялись. Не открывать порт Kuma в интернет ради ввода токена.
- До изменения Kuma подготовить новую зашифрованную online-копию её SQLite-базы и проверить восстановление в отдельную папку. Сентябрьский успешный backup не заменяет свежую копию.
- Проверить установленный collector, два последовательных цикла, неизменность fallback и изоляцию диагностических групп. Наличие кода в репозитории не подтверждает активацию на NAS.

## Поля штатной интеграции

В закрытой настройке уведомлений выбрать Telegram. Владелец вводит Bot Token, указывает Chat ID и, если нужно, Message Thread ID. Адрес API — штатный `https://api.telegram.org`. Не использовать ссылки с токеном в адресной строке браузера. Форма поддерживает скрытый ввод токена, получение Chat ID и plain-text шаблоны; эти возможности сверены с [кодом формы Kuma 2.3.2](https://github.com/louislam/uptime-kuma/blob/2.3.2/src/components/notifications/Telegram.vue).

Для проектного уведомления использовать формат Plain Text и [готовый шаблон](../deploy/monitoring/telegram-template.txt). Интеграция отправляет сообщение через Telegram API; успешный ответ Kuma нельзя подменять подтверждением получения человеком. [Provider Kuma 2.3.2](https://github.com/louislam/uptime-kuma/blob/2.3.2/server/notification-providers/telegram.js).

## Мониторы и проверка

Создавать только после защищённого входа и backup:

| Монитор | Ключ publisher | Что показывает |
|---|---|---|
| VLESS-NL | `WG-IMP` | Подтверждённые наблюдения основного выхода |
| HY2-DE | `HY2-USA` | Подтверждённые наблюдения резервного выхода |
| Мониторинг шлюза | `collector` | Наличие достоверных контрольных данных |
| Тест уведомлений | отдельный тестовый токен | Проверку доставки без остановки VPN |

Назначить уведомление только этим мониторам, не включать глобальную рассылку для посторонних сервисов. Push-токены хранить отдельно в root/private файле `0600`, не в этой инструкции. Их URL не печатать и не открывать извне.

Целевое поведение проекта: подтверждение отказа после 600 секунд непрерывных неудачных наблюдений, восстановление после двух успешных циклов, отсутствие данных после 180 секунд — отдельное состояние. Минутный publisher; напоминания не чаще раза в час. Точные параметры timeout/retry/resend проверить на установленной Kuma до включения уведомлений, не переносить число heartbeat в секунды по предположению.

Приёмка на отдельном тестовом мониторе: тест доставки, длительный отказ, восстановление, потеря/возврат heartbeat, ограничение повторов. Пользователь подтверждает получение сообщения. Не выключать рабочие VLESS/HY2 для такой проверки. Сохранить в отчёт только время, тип события и факт получения, без токенов и клиентского трафика.

## Пока остаётся открытым

HTTPS-доступ к Kuma, защищённый ввод токена, выбор получателя, актуальный backup, live-настройка мониторов и реальная доставка. Off-host наблюдателя нет: если весь NAS или его интернет отключён, мгновенное сообщение от этого же NAS не гарантируется.
