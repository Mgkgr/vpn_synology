# Обслуживание комплекса: состояние реализации

28.09.2026. Это локальная подготовка, **не отчёт о развёртывании на NAS**. Работающие VPN, клиентские ключи, правила и контейнеры в ходе этой работы не менялись.

## Что подготовлено

- Реестр компонентов, доверенные источники версий и pin образов. Найденный новый релиз не означает разрешение установить его.
- Root-worker: закрытый Unix-протокол, постоянные ID/этапы заданий, журнал намерений, общая блокировка обслуживания и изменений клиентов/правил/GeoData. Без Docker socket в публичной панели.
- Подтверждение паролем владельца, короткоживущий одноразовый grant, привязка к текущей сессии, операции и ревизии. Обычный администратор видит состояние без права обслуживания.
- Проверенные на фикстурах restart/update/rollback-оркестраторы: порядок зависимостей, отказ при неизвестной схеме БД или непроверенном backup, один безопасный recovery pass, сохранение неопределённого результата после обрыва.
- Scoped Docker adapter: проверка project/service, image ID, хешей mounts/capabilities/настроек, root-owned Compose и network namespace. Start/stop используют проверенный неизменяемый ID. Compose recreate ограничен зависимыми сервисами, без `down`, удаления томов, pull/build или посторонних проектов.
- Restic adapter и online SQLite backup, проверка содержимого восстановленной копии в отдельном закрытом каталоге, лимиты размеров, запрет traversal/symlink. Тест SQLite реально включает последний commit из WAL. Старый произвольный `TARGET_DIR` больше не удаляется. Неизвестный фактический формат persistence блокирует backup/update.
- `/system/components`: версии/digest/расхождения, ручная проверка версий, перезапуск отдельного сервиса/комплекса, подготовка пакетного обновления и восстановления точного snapshot. Остановленные сервисы требуют явного согласия; новый grant нужен для отката с потерей более новых данных.
- Пароль остаётся только в форме и очищается. После отправки ID хранится в URL, при потерянном ответе идут только GET того же задания, не повторный POST. Опрос 2 секунды первые 30 секунд, затем 5; в скрытой вкладке остановлен. Обычный inventory — раз в минуту.
- Локальный планировщик проверки **метаданных** в 05:00 по времени NAS, один catch-up, минутный лимит ручной проверки, защита от обратного скачка часов. Сам по себе ничего не устанавливает. Он ещё не подключён к установленной задаче DSM.

## Что ещё не завершено / не проверено на NAS

1. Root-discovery настоящих БД wg-easy/Kuma и схем/полей конфигурационной ревизии; manifest источников, путей и runtime contracts. Нельзя угадать эти сведения по названию контейнера.
2. Конкретные host-side readiness probes и update driver для установленной схемы: isolated candidate validation, production restore, проверка совместимости базы/образа. Тестовые драйверы не доказывают эти действия на NAS.
3. Сборка runtime, установка worker/DSM boot+watch, read-only монтирование сокета, затем отдельная приёмка restart/update/rollback. Пока executor не подтверждён, submit отказывается создавать задания, UI остаётся read-only. `maintenance_enabled` по умолчанию выключен.
4. Рабочий Restic/repository/password file: в проверенных стандартных путях NAS Restic не найден. Репозиторий не создавался; реальные production-бэкапы этой реализацией не выполнялись.
5. Импорт событий обслуживания в общий журнал/health-context и отдельные служебные сообщения через фактически установленный provider Kuma. Это остаётся частью задачи 5, не считается готовым Telegram-оповещением. Доставка пользователю не проверялась.
6. AntiDPI: preflight дал **unknown**, не `unsupported`. NFQUEUE-файлы с подходящим vermagic есть, но owner/CONNMARK и полный Docker inventory требуют уточнения; отдельный NFQUEUE-bind ещё не согласован. [Отчёт](diagnostics/2026-09-27-antidpi-preflight.md).

## Важные ограничения развёртывания

Не включать worker-флаг только ради появления кнопок. Не использовать новые backup shell wrappers до установки root-кода и reviewed manifest: они намеренно откажутся, ничего не удаляя. Не заменять текущую задачу backup неподготовленной новой.

Старый deploy helper не умеет применять `compose.versions.yaml`. Поэтому при появлении pins старый `run-dashboard-deploy.sh` блокируется, а не незаметно возвращает старый образ. Переход на worker-managed deploy требует подготовки и проверки конкретного установщика.

Ни один release не разрешён к установке только потому, что автотесты прошли. На NAS нужны проверенный encrypted backup, root-readiness, точные contracts/approved migration и отдельно согласованная приёмка. Не отключать рабочие VPN ради имитации отказа.

## QA

Локальная UI-проверка: `http://127.0.0.1:5189/system/components`, Playwright, 1366×900 и 390×844, тестовые ответы API. Проверены реальный рендер, кнопки, отсутствие framework overlay, фокус модального окна, Escape, зависимость WireGuard → Mihomo и отсутствие горизонтального переполнения. Ошибки первоначального тестового перехватчика API исправлены; после повторной загрузки ошибок приложения не обнаружено. Это не проверка опубликованной панели.

Авторская проверка без агентов — по просьбе пользователя. Она не заменяет независимую проверку root-исполнителя и live-приёмку.
