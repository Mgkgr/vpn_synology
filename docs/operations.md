# Эксплуатация VPN Dashboard

## Backup и восстановление

`deploy/scripts/backup-dashboard.sh` создаёт консистентный SQLite snapshot, сохраняет закрытую конфигурацию dashboard и persistent-конфигурацию VPN-шлюза в зашифрованный Restic-репозиторий. Пароль Restic хранится отдельным файлом с правами `0600`; он не попадает в Git или Hyper Backup логи.

Synology Task Scheduler запускает backup ежедневно в 03:30 `Asia/Yekaterinburg`. Hyper Backup должен реплицировать каталог `/volume1/docker/vpn-gateway/backups/dashboard/restic`. Раз в месяц запускается `restore-verify.sh`; он выполняет `restic check`, восстановление в scratch-каталог и `PRAGMA integrity_check`.

Перед аварийным восстановлением остановите dashboard, восстановите последнюю snapshot-копию, верните `dashboard.env` с исходным `DASHBOARD_ENCRYPTION_KEY`, затем запускайте проект. Новый ключ шифрования без миграции сделает сохранённые credentials wg-easy недоступными.

## Безопасное развёртывание

Перед первым запуском hardened-версии root выполняет `deploy/scripts/prepare-runtime.sh`. Он проверяет обязательный ключ, требует localhost-bind, переводит только данные dashboard и его управляемые rule-файлы к непривилегированному UID `10001`, затем запускает `docker compose config --quiet`. Скрипт не перезапускает `vpn-wireguard`, Mihomo или wg-easy.

Dashboard не получает bind-mount каталога Mihomo целиком: ему доступны только `GeoIP.dat`, `GeoSite.dat` в режиме чтения и каталог `rules` для управляемых DIRECT-правил. Конфигурация Mihomo и outbound-секреты не монтируются в контейнер панели.

DSM Reverse Proxy должен направлять `https://roaring.crazedns.ru:10443` на `http://127.0.0.1:8088`. Прямой доступ к `8088` из LAN и WAN после этого отсутствует.

Для повторяемого обновления используется `deploy/deploy-hardened.ps1`. Он передаёт на NAS архив только из Git HEAD, поэтому не затирает `dashboard.env`, SQLite, rule revisions и backup. Скрипт потребует пароль sudo один раз для preflight, после чего вызывает уже ограниченный `vpn-dashboard-deploy` и status-check.

Образы в `Dockerfile` зафиксированы одновременно конкретным тегом и digest. Их не обновляет Watchtower: новый digest выбирают вручную после проверки upstream release notes, полного CI и пробной сборки.

## График трафика

Collector запрашивает первый безопасно ограниченный sample `/traffic` Mihomo ровно раз в минуту и записывает только скорость входящего и исходящего канала в SQLite. Обзор читает эти уже сохранённые точки — переключение 5 минут / 30 минут / 6 часов и периодическое обновление страницы не создают новых запросов к Mihomo. История minute-level хранится семь суток и затем удаляется ежедневной retention-задачей.

## Состояние NAS и контейнеров

Для карточки «Хост DS923+» DSM Task Scheduler запускает от `root` один лёгкий скрипт раз в минуту:

```sh
/bin/sh /usr/local/libexec/vpn-gateway/collect-host-health.sh
```

`deploy/scripts/repair-host-health.py` устанавливает проверенную копию сборщика в каталог, принадлежащий root, создаёт задачу `VPN Dashboard — host health` через штатный API DSM и проверяет её расписание: ежедневно, 00:00–23:59, каждую минуту. Повторный запуск не создаёт дубликаты; совпадение имени с другой командой или неполное расписание останавливают установку для ручной проверки. Скрипт проверяет SHA256 исходного сборщика: при обновлении его кода необходимо сначала проверить изменения, затем обновить ожидаемый SHA256 и установленную root-копию. Контейнеры не перезапускаются.

После установки сборщик можно запускать вручную приведённой выше командой. Первый снимок содержит `cpu_usage_percent=null`, процент CPU появляется со второго запуска. Старый `deploy/setup-host-health.ps1` создаёт только разовый снимок и сам по себе не устанавливает расписание. При ручном создании задачи в DSM используйте root-копию сборщика, а не скрипт из каталога, доступного на запись обычному пользователю.

Скрипт читает только `/proc`, `df` и состояние пяти известных контейнеров через Docker CLI. Он записывает один атомарный JSON-снимок в `deploy/data/host-health.json`; контейнер панели читает его как непривилегированный UID `10001`, Docker-сокет в контейнер не монтируется. На первом запуске CPU отображается как «первая точка», потому что ещё нет предыдущего счётчика; начиная со второго виден процент использования CPU. Статус `absent`, рост числа перезапусков, ошибки/потери сети, нехватка памяти, swap и места на томе — признаки, которые нужно проверять до диагностики самого VPN.

Важно: строка «Ошибки сети» в этой версии показывает счётчики интерфейсов `/proc/net/dev`. Это не счётчики переполнения UDP-сокетов: `Udp.RcvbufErrors` нужно проверять отдельно. Наличие данных само по себе не доказывает здоровье хоста — проверяйте также время снимка и состояния контейнеров.

## Приёмные UDP-буферы Docker

На DS923+ были подтверждены потери в сокетах `docker-proxy`, обслуживающих UDP/51820, при исходном `net.core.rmem_default=212992`. `deploy/scripts/repair-udp-receive-buffers.py apply` поднимает только `rmem_default` и `rmem_max` минимум до 4 МиБ. Более высокие существующие значения не уменьшаются; передающие буферы, маршрутизация и Docker daemon не меняются.

Настройка сохраняется в `/etc/sysctl.d/90-vpn-gateway-udp-receive.conf`, исходные значения — в root-only `/usr/local/etc/vpn-gateway/udp-receive-before.json`. Команда `restore` возвращает исходные параметры и прежнее состояние этого sysctl-файла. Ошибка применения вызывает откат частичных изменений. После обновлений DSM следует повторно проверить фактические значения; полная перезагрузка NAS не является частью автоматической проверки.

Изменение применяется к новым сокетам, не увеличивая буферы уже открытых. Для немедленного применения ко всем VPN-клиентам требуется согласованный краткий перерыв. `deploy/scripts/restart-gateway-transport.py` останавливает только Mihomo → WireGuard, запускает WireGuard → Mihomo, проверяет готовность и неизменность ключей/AllowedIPs. Он не меняет конфигурации и образы. Запуск отделяется от SSH-сеанса, поскольку сам SSH может идти через перезапускаемый VPN. После запуска выполняется ограниченное наблюдение host/gateway UDP-счётчиков и актуальности health-снимков. Повторный запуск с существующим отчётом запрещён: сначала изучите результат предыдущего запуска.

## Локальные зашифрованные резервные копии

Restic хранит на самом DS923+ snapshot базы панели, владельцев и сессий, зашифрованные учётные данные wg-easy, файлы секретов панели, WireGuard-профили/ключи и persistent-данные Mihomo, wg-easy и Uptime Kuma. За счёт этого восстановление не требует перевыпускать конфигурации клиентам.

Файл пароля Restic должен быть отдельным, с правами `0600`, например `/volume1/docker/vpn-gateway/secrets/restic-password`. В DSM Task Scheduler нужны две задачи от `root`:

```sh
RESTIC_PASSWORD_FILE=/volume1/docker/vpn-gateway/secrets/restic-password BACKUP_TIER=frequent /volume1/docker/vpn-dashboard/deploy/scripts/backup-dashboard.sh
```

— раз в 5 минут, и та же команда с `BACKUP_TIER=daily` — раз в сутки в 03:30. Retention хранит 288 последних точек (24 часа при пятиминутном запуске), 14 дневных, 8 недельных и 12 месячных. Раз в месяц запускайте `restore-verify.sh` с тем же `RESTIC_PASSWORD_FILE` — он проверяет Restic, SQLite и наличие Dashboard/WireGuard persistence в restore-копии.

Это локальная защита от ошибки, не защита от утраты самого NAS. Внешняя репликация намеренно не включена в текущем релизе.

## Fallback и OpenAI

Цепочка выхода остаётся одной: `VPS-FALLBACK = WG-IMP → HY2-USA`. Панель не создаёт отдельный OpenAI-канал: при первом корректном старте она добавляет только отсутствующее правило `GEOSITE,openai → VPS-FALLBACK`. Уже созданное администратором правило для OpenAI не меняется. Это сохраняет выбранный режим «Авто VPN» и позволяет в «Правилах» при необходимости назначить OpenAI прямо на WG-IMP, HY2-USA или DIRECT.

14 сентября 2026 года исходящий профиль с техническим именем `WG-IMP` был переведён на **VLESS TCP + REALITY + Vision (США)**, а не WireGuard, с отображаемым именем `VLESS-USA`. 27 сентября основной профиль заменён на `VLESS-NL`, резерв — на `HY2-DE`; подробности и ограничения проверки приведены ниже. Внутренние ID `WG-IMP` и `HY2-USA` сохранены для совместимости с существующими правилами и историей; фильтр журнала преобразует отображаемые имена в эти ID. Входной WireGuard/wg-easy, адреса и ключи клиентов не менялись. Не определяйте реальный протокол или географию по старому ID в техническом API: проверяйте поле `type` в Mihomo и фактический внешний IP. Отображаемые имена относятся к текущим профилям, а не к географии исторических событий.

Точечная миграция реализована в `deploy/scripts/replace-primary-vless.py`: профиль поступает через stdin, отдельный процесс Mihomo v1.19.28 проверяет его только на loopback без TUN и DNS. После проверок сохраняется зашифрованная копия конфигурации и проверяется её расшифровка. Затем применяется конфигурация через controller без перезапуска контейнеров; файл сохраняется только после проверок рабочего выхода. Ошибка проверки вызывает возврат к конфигурации на диске. Скрипт не переименовывает правила и не меняет интервал fallback.

Результат выполненной миграции хранится на NAS в `/volume1/docker/vpn-gateway/.vless-maintenance/job-2rfdqz05/status.json`; там же — `config-before.enc`. Ключ копии хранится отдельно в домашнем каталоге `prometei`, в `.vpn-gateway-backup-keys/job-2rfdqz05.key`, с правами `0600`. Эти файлы не включаются в Git. При переносе резервной копии сохраните и закрытый файл ключа.

`deploy/apply-fallback-policy.ps1` устанавливает approved health-check интервал `30` секунд, строго проверяет, что состав и порядок fallback не изменились, проверяет Mihomo-конфигурацию в контейнере и делает backup перед перезапуском только Mihomo. Скрипт **не** отключает WG-IMP или HY2-USA, поэтому не является имитацией аварии. Итог `FAILOVER_EXERCISE=not_run` — ожидаемый: фактическую проверку переключения проводят отдельным согласованным окном, когда короткое отключение выхода допустимо.

### Приоритет OpenAI при закреплённой общей AI-категории

14 сентября 2026 года политика `GEOSITE,openai` переведена на `VPS-FALLBACK`. При проверке реальных соединений обнаружено, что более ранний `managed-wg-imp` содержал общую категорию `category-ai-!cn`, поэтому одно изменение политики OpenAI не меняло фактический маршрут.

На NAS добавлено узкое правило перед `managed-wg-imp`, после DIRECT-провайдеров:

```text
AND,((GEOSITE,openai),(RULE-SET,managed-fallback)),VPS-FALLBACK
```

Оно меняет приоритет только пересечения OpenAI с активным набором автоматической маршрутизации, не переводя остальные AI-сервисы на резерв. Преобразование конфигурации находится в `deploy/scripts/prioritize-openai-fallback.py` и покрыто тестами. Это точечное разрешение текущего конфликта, а не универсальный механизм приоритетов категорий: при изменении общих AI-политик нужно повторно проверять пересечения. Старые TCP-соединения сохраняют прежнюю цепочку до переподключения; для проверки используются новые соединения.

Зашифрованная копия политик перед изменением: `.vless-maintenance/chatgpt-fallback-fhn2ys1s/config-before.enc`; копия полной конфигурации перед изменением приоритета: `.vless-maintenance/openai-priority-ylbiw72m/config-before.enc`. Оба пути находятся внутри `/volume1/docker/vpn-gateway`. Ключи расположены отдельно в домашнем каталоге `prometei`, `.vpn-gateway-backup-keys`, и не включаются в Git.

### Замена резервного Hysteria2-профиля

Следующая команда относится к прежней миграции `HY2-NL` → `HY2-USA` с port-hopping. Она требует диапазон портов и **не подходит** для нового профиля от 27.09.2026 без `mport`; для него используется расширенный `deploy/scripts/replace-primary-vless.py`, описанный ниже.

```powershell
D:\Projects\vpn-gateway-dashboard\deploy\replace-hy2-profile.ps1
```

Скрипт запросит два секрета в маскированном вводе, поэтому они не попадут в историю PowerShell, исходный код, вывод или Git. Он передаёт на NAS временный файл с правами `0600`, сохраняет закрытый backup прежнего `hysteria2.env` и `config.yaml`, затем атомарно меняет `HY2-NL` на `HY2-USA` в Hysteria2-блоке, fallback-ссылке и provider правил. Политики из панели, GeoData, список правил и `WG-IMP` не пересоздаются и не отключаются.

Новый профиль проходит три проверки: синтаксис полной текущей конфигурации Mihomo, hot-reload через аутентифицированный controller и отдельный `proxy_delay` непосредственно через `HY2-USA`. `ports` включает port-hopping в формате Mihomo; при ошибке любой проверки применяются прежние secret/config и выполняется reload предыдущей версии. Перезагрузка controller может кратко оборвать SSH, и это не считается ошибкой: launcher ожидает опубликованный итоговый статус. Успешный вывод содержит `HY2_DELAY_MS`, `HY2_PORT_HOPPING=enabled` и путь к закрытому backup, но не содержит ключей.

- Технические имена, порядок `WG-IMP → HY2-USA`, 15 правил Mihomo и клиентские ключи сохранены. WireGuard и Mihomo не перезапускались; использован hot-reload. Отдельно пересобран только dashboard для новых подписей.

`deploy/scripts/replace-primary-vless.py` теперь принимает VLESS или Hysteria2 через stdin JSON. Он меняет только соответствующий выход, проверяет изолированную копию, создаёт зашифрованный backup, проверяет расшифровку и применяет конфигурацию с откатом при ошибке. Секреты не передаются аргументами командной строки. Файл `secrets/hysteria2.env` на NAS синхронизирован с новым резервом и имеет права `0600`; его прежняя версия также сохранена зашифрованной.

`deploy/scripts/verify-isolated-fallback.py` проверил реальное переключение отдельного процесса Mihomo: оба выхода доступны → основной недоступен только в тестовой конфигурации → резерв передаёт HTTPS → основной восстановлен. В тесте нет TUN, слушатели доступны только на loopback, рабочая конфигурация проверена по SHA-256 и не изменена. Процесс, тестовые конфигурация и бинарный файл удалены после завершения. Интервал теста — 2 секунды; **в production обнаружен интервал 300 секунд, он не менялся**. Скорость тестового переключения не является обещанием такой же скорости на клиентах; существующие TCP-сессии при отказе всё равно требуют переподключения.

У нового VLESS была одна неудачная проверка в 11:05, затем 240 мс в 11:10 и 5129 мс в 11:15. Оба выхода в конце наблюдения доступны, выбран VLESS. Это подтверждает работоспособность нового резерва, но **не подтверждает устранение всех обрывов основного канала**.

## MAX — мессенджер, DIRECT

По состоянию на 15 сентября 2026 года домены MAX включены в широкую категорию `mailru-group` в [исходном GeoSite](https://github.com/v2fly/domain-list-community/blob/master/data/mailru-group). Пункт `VK` (`geosite:vk`) не равнозначен этой категории. Для узкой маршрутизации самого мессенджера подготовлен `deploy/rules/max-messenger-direct.txt`:

```text
DOMAIN-SUFFIX,max.ru,DIRECT
DOMAIN-SUFFIX,oneme.ru,DIRECT
```

В панели эти строки добавляются к существующему содержимому «04 Правила → Свой DIRECT-список» и применяются кнопкой «Применить DIRECT-правила». Не заменяйте ими весь список. Корневой `max.ru` охватывает веб-версию, загрузки и поддомены сервиса; `oneme.ru` — дополнительную доменную инфраструктуру MAX. Для узкого правила не требуются `max.com`, общие IP-сети VK или вся категория Mail.ru. Домены Сферума из соседнего раздела upstream в этот набор намеренно не включены.

Альтернативный импорт с проверкой, зашифрованной резервной копией и пропуском дублей:


## Суточные замеры плиток — локальная поставка 04.10.2026

Код подготовлен, **на NAS не внедрён; `SITE_PROBES_ENABLED=false`**. Обычный deploy нельзя запускать из смешанной dirty-копии без отдельного согласования набора файлов. Реализация и результаты проверки: [протокол поставки](diagnostics/2026-10-04-daily-service-probes.md).

В разделе «04 Правила» результаты находятся прямо под плиткой. Нажатие раскрывает назначение маршрута и сведения по контрольному URL: DIRECT, основной и резервный выход, дата, задержка и безопасное объяснение ошибки. Раздел не запускает сетевой тест при открытии: один общий GET читает SQLite, затем обновляется раз в минуту только в видимой вкладке. При ошибке этого GET редактирование правил остаётся доступным, старые результаты теряют положительную подсветку.

- Каталог — 36 фиксированных сервисов; до 108 проверок в сутки. Произвольные URL и содержимое DIRECT-списка не сканируются.
- Расписание: 04:30 `Asia/Yekaterinburg`. После старта допускается один догоняющий прогон текущей даты; старые дни не догоняются. Claim даты сохраняется в БД: рестарт и второй процесс не дублируют начатую пачку. Опрос расписания раз в минуту, поэтому запуск не обязан совпасть с точной секундой 04:30:00.
- Один сетевой тест одновременно, таймаут Mihomo 10 секунд / controller 12 секунд, пачка максимум 25 минут. Результаты сохраняются по одному; прерывание не превращается в «все сайты недоступны». Повтор этой даты автоматически не запускается.
- Результаты старше 25 часов и результаты прошлого неполного прогона явно отмечены; история хранится 30 дней. Подпись маршрута сохраняется вместе с результатом, не переименовывается задним числом.
- Проверяется HTTPS HEAD, а не ICMP ping, вход в приложение, видео, UDP или пропускная способность. Редиректы не выполняются. HTTP-ответ вне 2xx/3xx не равен отказу VPN; точный HTTP-код/причина TLS могут быть недоступны в API.
- DNS A/AAAA предварительно проверяются через Mihomo: пустые, частные, loopback, FakeIP и некорректные ответы останавливают HEAD. Эта проверка не закрепляет DNS-ответ на время последующего соединения. Пользовательские адреса потому не разрешаются.
- Перед HEAD требуется подтверждённый `unified-delay=false`: иначе Mihomo может выполнить второй HEAD. Код возвращает `unknown/probe_mode_invalid` и **не меняет глобальную настройку**.

### Приёмка на NAS — отдельный этап

1. Выбрать согласованный набор локальных изменений, повторить тесты/secret scan. Сохранить текущую БД и конфигурацию в свежую локальную зашифрованную копию; проверить расшифровку в отдельную папку. Не включать копию/ключ/SQLite в Git.
2. Считать SHA-256 исходного `config.yaml`. Чистая функция `configure_site_probes(text)` в `deploy/scripts/configure-site-probes.py` создаёт только три скрытые singleton-select группы: `DASH-SITE-DIRECT`, `DASH-SITE-WG-IMP`, `DASH-SITE-HY2-USA`. Она сама не читает/пишет NAS и не вызывает reload. Неизвестный layout/коллизия/изменённый собственный блок → остановка.
3. В отдельной изолированной копии проверить `/mihomo -t`, три группы, `interval: 0`, `empty-fallback: REJECT`, `unified-delay=false`. Проверить установленную версию, структуру per-URL `extra`, класс HTTP-ответа и отсутствие изменения history/alive рабочих выходов от теста wrapper. Обычные фоновые проверки рабочего fallback могут менять history сами; сравнение требует изоляции и корреляции времени, а не простого равенства двух живых снимков.
4. Проверить, что новые группы не попали в рабочие группы/правила клиентов; DNS, firewall, ключи, fallback и другие проекты вне собственного блока не изменены. При расхождении исходного SHA-256 остановиться (CAS), а не перезаписывать параллельную правку.
5. Только в согласованное окно применить валидированную конфигурацию с rollback и reload. Не отключать работающий VPN для проверки fallback. Если изоляция не доказана, флаг остаётся выключенным.
6. После приёмки включить `SITE_PROBES_ENABLED=true` в закрытом `deploy/dashboard.env`, пересоздать **только dashboard** для чтения env. Проверить `GET /api/rules/service-checks`: `enabled`, часовой пояс, первый `run`, отдельные результаты и следующий запуск. До 04:30 запрос не запускает пачку.
7. Убедиться, что обновление/раскрытие страницы не вызывает HEAD, по окончании прогона есть `completed_count`, а `completed` не трактуется как успех каждого сайта. Перезапуск dashboard в ту же дату не повторяет измерения.

SQLite получает три новые additive-таблицы `site_probe_schedule`, `site_probe_runs`, `site_probe_results` при штатном `create_all`; существующие данные клиентов и правила не переписываются. Watermark расписания не удаляется при очистке 30-дневной истории. Для отката функции выключить флаг и вернуть прежний образ dashboard; не удалять БД. Если удаляются diagnostic-группы, делать это отдельной проверенной конфигурационной операцией.

## Российские маркетплейсы и доставка

Точные GeoSite-категории `ozon`, `wildberries`, `avito` и `yandex` назначаются в панели на `DIRECT`. Они лучше ручных корневых доменов для соответствующих сервисов, потому что обновляются вместе с GeoSite. `yandex` намеренно широк: Еда, Лавка и Go используют общие домены авторизации и инфраструктуры Яндекса.

Для Самоката и распространённых сервисов доставки используется отдельный проверенный импорт:

```powershell

```

Импортёр нормализует только `DOMAIN-SUFFIX,...,DIRECT`, игнорирует уже существующие строки, создаёт зашифрованный backup и применяет один reload через `RuleService`. При неуспешном reload предыдущий `direct.txt` восстанавливается. Не добавляйте к этому набору IP-адреса CDN: сначала захватите трафик конкретного телефона.

```powershell

```

Пустой `-SourceAddress` означает наблюдение всех текущих клиентов. Для точного клиента передайте его VPN-адрес, например `-SourceAddress 10.66.0.5`. Диагностика read-only и выводит только адрес источника, домен или IP назначения, тип транспорта, применённое правило и цепочку — без ключей, конфигураций и секретов.

Чтобы правила из панели применялись, один раз запускается `deploy/configure-managed-rules.ps1` после развёртывания. Скрипт допускает только известную текущую структуру `direct-custom`, создаёт четыре file-provider (`managed-direct`, `managed-fallback`, `managed-wg-imp`, `managed-hy2-usa`), сохраняет зашифрованный backup и валидирует конфигурацию в Mihomo. При неизвестной или частично изменённой структуре он завершится без догадок и без изменения маршрутизации. После успешного запуска он перезапускает Mihomo и dashboard: на новом запуске dashboard создаст отсутствующее правило OpenAI → VPS-FALLBACK.
